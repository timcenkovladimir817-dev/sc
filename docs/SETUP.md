# Арматура PRO — админка, учётные записи и прогресс

Система закрытая: самостоятельной регистрации нет, учебные материалы доступны только после
входа. Администратор или наставник приглашает сотрудника; сотрудник задаёт пароль по ссылке
из письма. Наставник (роль `teacher`) видит прогресс учеников и выгружает результаты в панели;
руководитель смотрит прогресс по отдельной ссылке без учётной записи.

## 1. Первый администратор

Это единственный шаг, который нельзя сделать из интерфейса: администратора ещё нет,
поэтому приглашать некого.

1. Supabase → **Authentication → Users → Add user**.
2. Укажите рабочий email и пароль. Включите **Auto Confirm User**, иначе вход не сработает
   до подтверждения письма.
3. Supabase → **SQL Editor**. Откройте `supabase/bootstrap-admin.sql`, замените
   `admin@example.com` на свой email и выполните файл целиком.
4. В конце запроса должен появиться ваш email с `role = admin`.
5. Откройте `/login.html`, войдите и перейдите в `/admin/`.

Если профиль не появился, создайте его вручную:

```sql
insert into public.profiles (id, full_name, email, role, is_blocked)
select id, coalesce(raw_user_meta_data->>'full_name', ''), email, 'admin', false
from auth.users
where lower(email) = lower('admin@example.com')
on conflict (id) do update set role = 'admin', is_blocked = false;
```

## 3. Настройки Authentication

Supabase → **Authentication**:

1. **Providers → Email**: отключите **Allow new users to sign up**. Доступ только по приглашению.
   В текущем проекте эта настройка ещё включена (`disable_signup = false`), поэтому её нужно
   выключить вручную: иначе любой может создать себе аккаунт через API Supabase, даже если
   на сайте нет формы регистрации.
2. **URL Configuration**:
   - Site URL: `https://timcenkovladimir817-dev.github.io/sc`
   - Redirect URLs (можно с подстановкой `**`):
     `https://timcenkovladimir817-dev.github.io/sc/**`
   - Для локальной проверки добавьте адрес своего локального сервера, например:
     `http://localhost:3000/**` или `http://localhost:8000/**`.

   Важно: `redirectTo`, который передаёт сайт при запросе сброса пароля, действует
   только если этот адрес входит в Redirect URLs. Если его там нет, Supabase молча
   подставляет Site URL, и письмо ведёт на корень сайта (а не на `/reset.html`) или
   вовсе на чужой адрес. Поэтому при смене домена обновляйте и Site URL, и список.
3. **Email Templates**: письмо приглашения отправляет не Supabase, а Edge Function через
   Яндекс SMTP. Встроенные письма Supabase нужны только для восстановления пароля.
4. Пароль — не короче 10 символов. Это проверяет `reset.html`.
5. Первого администратора создавайте с включённым **Auto Confirm User**: в проекте
   `mailer_autoconfirm = false`, без этого вход не сработает до подтверждения письма.

## 4. Секреты Edge Functions

Supabase → **Edge Functions → Secrets**:

```text
SITE_URL=https://timcenkovladimir817-dev.github.io/sc
ALLOWED_ORIGIN=https://timcenkovladimir817-dev.github.io
BITRIX_WEBHOOK_URL=https://ваш-портал.bitrix24.ru/rest/1/xxxxxxxxxxxx/
YANDEX_SMTP_USER=training@ваша-компания.ру
YANDEX_SMTP_PASSWORD=пароль-приложения
YANDEX_SMTP_HOST=smtp.yandex.ru
YANDEX_SMTP_PORT=465
MAIL_FROM_NAME=Учебный центр
```

`SUPABASE_URL`, `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY` Supabase передаёт функциям
автоматически. Ключ `service_role` нельзя вставлять в `js/config.js` или в HTML.

Для Яндекса нужен **пароль приложения**, а не обычный пароль от почты.

## 5. Публикация функций

Через CLI:

```bash
supabase functions deploy invite-user --no-verify-jwt
supabase functions deploy resend-invite --no-verify-jwt
supabase functions deploy block-user --no-verify-jwt
supabase functions deploy send-reminders --no-verify-jwt
```

`--no-verify-jwt` нужен потому, что функция сама проверяет токен и роль администратора
через `profiles`. Через панель Supabase функции можно загрузить вручную: создайте функцию
с тем же именем и вставьте содержимое `supabase/functions/<имя>/index.ts` вместе с папкой
`_shared`.

Проверка без входа: запрос к функции должен вернуть `401 {"ok":false,"error":"Нет авторизации"}`.
Если возвращается `404`, функция не развёрнута.

## 6. Bitrix24

1. Создайте входящий webhook с правами `tasks` и `user`.
2. URL скопируйте в секрет `BITRIX_WEBHOOK_URL`.
3. Сотрудник, наставник и руководитель должны существовать в Bitrix24 с теми же email.
4. Задача создаётся методом `tasks.task.add`: ответственный — сотрудник,
   наблюдатели — наставник и руководитель.
5. Если сотрудник не найден, приглашение всё равно создаётся: ошибка попадёт
   в `invitations.bitrix_error`, в письмо-предупреждение и в `notification_log`.

## 7. Ежедневная работа

### Кто что может

- **Администратор** (`admin`): приглашения, роли, блокировка, сброс пароля, удаление,
  напоминания о сроках, журнал действий, диагностика, схемы из репозитория, статистика.
- **Наставник** (`teacher`): приглашать учеников, следить за прогрессом и статусами,
  смотреть статистику по ученикам, дополнять материал (редактор книги, иллюстрации,
  главы в базу), выгружать CSV.
- **Ученик** (`student`): только свой курс и свой прогресс.

### Пригласить сотрудника

`admin/index.html` → «Пригласить сотрудника»: ФИО, email, должность, подразделение,
наставник, руководитель, срок. После отправки:

- создаётся пользователь и назначение курса;
- создаётся ссылка на прогресс сроком 365 дней;
- создаётся задача Bitrix24;
- уходит письмо со ссылкой на задание пароля.

Если почта не настроена, после отправки панель покажет ссылку для задания пароля —
её можно передать сотруднику вручную. Для этого нужна обновлённая функция `invite-user`
(в ответе есть поле `inviteUrl`).

Ссылку на прогресс скопируйте в задачу или отправьте наблюдателям.

### Управлять пользователями

`admin/users.html`:

| Действие | Что делает |
|---|---|
| Поиск и фильтры | ФИО, email, должность; администраторы, сотрудники, заблокированные, без курса |
| Роль | Сотрудник / Наставник / Администратор. Нельзя менять себе и снять роль с последнего администратора |
| Заблокировать | Запрещает вход и чтение данных. Сессия перестаёт работать |
| Разблокировать | Возвращает доступ |
| Сбросить пароль | Отправляет письмо со ссылкой на `/reset.html` |
| Ссылка на прогресс | Новый токен на 365 дней, копируется в буфер |
| Удалить | Полное удаление: профиль, назначения, прогресс. Нужно ввести email для подтверждения |
| Экспорт CSV | Выгружает отфильтрованный список с курсом, прогрессом и сроком в `users-progress.csv` |
| Напомнить о сроке | Кнопка «Срок» у назначения и «Напомнить о сроках» в панели — письма через `send-reminders` |

Пароли сотрудников администратору недоступны — это правильно. Сброс идёт только письмом.

### Журнал действий

`admin/audit.html` показывает, кто и когда менял роли, блокировал вход, приглашал,
отзывал приглашения, отправлял письма и выдавал ссылки на прогресс. Записи только на чтение.

### Прогресс для наставника

Ссылка вида `/progress.html?token=…` не требует входа. Она перестаёт работать, если
приглашение отозвано, назначение отменено, пользователь заблокирован или истёк срок.
Ссылку можно отозвать в базе: `update progress_links set revoked = true where token = '…';`

### Статистика по ученикам

`admin/stats.html` показывает по каждому ученику: общий прогресс, процент по каждой главе
с заметками, лучший результат итогового теста, дату начала и последней активности, время
на курсе и просрочку срока. Есть поиск, фильтры и два CSV-экспорта — сводный и «по главам»
(таблица «ученик × глава»). Данные о тесте и активности появляются после применения
миграции `0008_student_statistics.sql` и повторного прохождения учеником теста.

## 8. Диагностика

Откройте `admin/diag.html`. Страница показывает:

- есть ли сессия и какой email;
- читается ли профиль через REST;
- роль и блокировку;
- доступ к таблицам;
- установлены ли `is_admin()`, `is_active_user()`, `admin_set_role()`, `admin_revoke_invitation()`, `admin_log_action()`;
- развёрнуты ли Edge Functions.

Типичные причины отказа:

| Симптом | Причина | Решение |
|---|---|---|
| «Доступ закрыт», роль `student` | Профилю не выдали `admin` | `bootstrap-admin.sql` или `update profiles set role='admin'` |
| Бесконечный переход на вход | Старый токен или неверный `next` | Ctrl+F5, войти заново |
| `permission denied for table` | Не применена `0003_security.sql` или нет профиля | Выполнить миграции, проверить `profiles` |
| «Функция не установлена» при смене роли | Нет `0004_admin_tools.sql` | Выполнить файл в SQL Editor |
| Письмо не приходит | Не заданы SMTP-секреты или пароль Яндекса обычный | Проверить Secrets, создать пароль приложения |
| `401 Нет авторизации` от функции | Истекла сессия | Войти заново |
| `404` от функции | Функция не развёрнута | Задеплоить заново |

## 9. Проверка перед публикацией

- [ ] Новый пользователь не может зарегистрироваться сам.
- [ ] Первый администратор входит и видит `/admin/`.
- [ ] `0004_admin_tools.sql` и `0005_progress_sync.sql` выполнены, смена роли и журнал работают.
- [ ] Сотрудник не видит чужие назначения и не может изменить себе роль.
- [ ] Прогресс сотрудника сохраняется в базе и виден по ссылке на прогресс.
- [ ] Заблокированный пользователь не может войти и читать данные.
- [ ] Ссылка на прогресс не открывается после отзыва.
- [ ] Письмо приходит, ссылка ведёт на `/reset.html`.
- [ ] Задача Bitrix24 создаётся с нужными наблюдателями.
- [ ] В `js/config.js` только publishable/anon ключ, `service_role` отсутствует.

## 10. Ограничения

- Лучший результат итогового теста хранится и в браузере, и в базе (колонка
  `enrollments.quiz_best`, миграция 0008). После входа берётся большее из двух значений.
- Прогресс по модулям и заметки ученика синхронизируются с базой после входа; без входа —
  только локально.
- Автоматическое закрытие задачи Bitrix24 при завершении курса — следующий этап.
- Учебные материалы открываются только после входа (проверка в `js/loader.js`). Главы и схемы
  лежат статическими JSON/SVG в репозитории; сам вход и права проверяются в Supabase, а не
  на уровне файлов — для строгой защиты файлов держите их в приватном хранилище.
- Удаление пользователя необратимо; для временного запрета используйте блокировку.
